# EZAgent judge demo: document workbench delivery and acceptance

Status: proposed replacement acceptance contract, 2026-10-15. This supersedes the 2026-10-14 CSV invoice-task contract as the product release target. Implementation and test evidence must be recorded separately; this document certifies no gate.

## Goal, source and protected boundary

A first-time judge can create/select a synthetic order inside EZAgent or describe custom work, review a quotation, invoice/payment request or receipt, and export a traceable document draft. The main EZAgent route is `/documents`. The existing `/invoice-demo` CSV processor remains a labeled legacy demo and rollback path; its prior tests are regression evidence, not proof of the new product journey.

The design reference is the separate Git repository at `inkvoice拷貝/Inkvoice`. Its **generic** layout and field structure may inform generic EZAgent components; the first style is not CantoNet-branded. Do not stage the nested repository, copy organization contact/bank/tax defaults, or read/copy `.env.cantonet`. Public EZAgent source contains only generic schema and synthetic fixtures. Real issuer profiles, bank details, customer information and order records need protected configuration/storage and an explicit data policy.

The local AI may propose bounded text and candidate fields from a custom description. It cannot decide an unknown price, quantity, tax, payment status, bank account or customer identity; these stay empty and require human entry or confirmation. Structured order values are copied deterministically with source ID/version and are never re-inferred by the model. No draft, AI suggestion or demo role switch sends a document, initiates payment or grants company approval.

The four phases below remain sequential **release gates**. Later implementation may proceed while an earlier gate awaits resources, but no later release claim is made early. The generic workflow builder remains configuration/preview unless an executor exists.

## Phase 1 — judge journey and bounded document workbench

Owner: Planner sets the contract; Worker B owns the user journey; Worker A owns bounded data/model service; Auditor verifies independently.

1. Home exposes four clear paths: prepare local AI, chat, design a workflow, and create a document. `/documents` has visible routes home and a clear choice between **From an order** and **Describe custom work**. `/invoice-demo` is labeled legacy and is not the primary call to action.
2. The first release has a manual order list **inside EZAgent**. A judge can create, save, find, select and edit a synthetic order with stable ID/version; editing creates a new version without rewriting an existing draft's source. The initial order schema includes buyer, currency, items with descriptions/quantity/explicit price, agreed dates/terms and source ID/version; missing facts stay null. Selecting an order copies only known values into a versioned draft, with field-level `order`, `user` or `AI suggestion` provenance. Reopening the same order creates a separate draft without consuming a final document number. If the order version changes, the draft shows the difference and requires review again. External order-system import is a later adapter and is not assumed for this gate.
3. Custom description invokes the local model for a narrow, schema-validated `DraftSuggestion`: supported text fields, candidate item descriptions, source excerpts and missing-field list. Unknown or conflicting fields remain blank; unsupported keys, invalid currency, negative quantity and fabricated price/payment/tax/bank values are rejected or left unapplied. The user selectively applies suggestions and sees source and confirmation state. Planning/suggestion alone never issues, exports or mutates an order.
4. The workbench supports quotation, invoice/payment request and receipt drafts with editable parties, items, dates and terms, deterministic totals in integer minor units and a paper preview. Tax is explicit policy/input, never an assumed fixed percentage. A receipt requires a human-confirmed or trusted-record payment amount and date. Missing required facts visibly block issuance. Saving/editing a draft increments a version and invalidates its review; no original order or issued record is silently overwritten.
5. For the judge build, the explicit action is named **Create sample document**, not a generic `Issue document` or `Approve`. It uses a **synthetic demo namespace** only and a generic InkVoice-inspired paper layout. The user sees an exact preview and a field-by-field checklist before confirmation; unconfirmed or edited drafts cannot create a sample or export as reviewed. The server atomically compares the persisted draft revision and review digest before creating the immutable sample; a stale edit returns 409. Creation requires an idempotency key, so retrying the same request returns the same sample and **sample** number, while concurrent distinct requests cannot duplicate a number. The sample is clearly marked `SAMPLE / NOT FOR PAYMENT`. Browser print/PDF output matches the reviewed version and totals, including multi-page behavior. No email, messaging, payment request dispatch, real customer document or formal company approval occurs. Real issuance policy and authenticated release remain Phase 4.
6. Execution and recovery states show progress, completion, error and retry/cancel where supported. Orders, drafts and sample snapshots live only in ignored local app data (development `.ezagent/documents/`; packaged macOS under its Application Support runtime), never `public/`, a long-lived seller-profile cookie or browser localStorage. They persist until the user explicitly deletes them; the UI provides draft deletion and a confirmed **Clear synthetic demo data** action. An order referenced by a draft/sample is archived or deletion is refused, never silently cascaded; clearing samples removes the demo records without reusing previous sample numbers or rewriting exported files. Document the location and retention/deletion effect, and test refresh/relaunch, delete, referenced-order handling and clear/recovery. Builder preview and Review demo say what is simulated. All key controls work by keyboard, have labels/focus/error text, and remain usable on a narrow mobile viewport. Test with at least five first-time nontechnical participants on desktop and mobile: measure completion time/rate, wrong clicks, help and false beliefs about AI, payment and approval. Fix critical misunderstanding before freezing the judge build; do not assert an unmeasured time-to-value.

Gate evidence: manual-order create/edit/version fixture plus custom-description fixture; a browser path for **each** quotation, invoice/payment request and receipt (including human-confirmed payment amount/date); schema and deterministic total tests; stale-review 409, same-idempotency-key retry returns the same sample/number, distinct-request number collision, edit-invalidation, refresh/restart, draft deletion, referenced-order protection, clear-demo-data and export/preview assertions; keyboard and mobile browser recording or reproducible notes; build/typecheck; five-person findings log. The prior CSV fixture and browser results do not close this gate.

## Phase 2 — downloadable local edition of the new workbench

Owner: Worker A packages/runtime and local model; Worker B supplies first-run copy; Auditor verifies on a clean machine or clean user account. First target: macOS arm64; Windows is a separate gate.

1. Produce a versioned signed or clearly marked development `.app` download with SHA-256, supported macOS/hardware/free-space/model-download requirements and illustrated no-terminal first run. Bundle the actual app runtime and required components; detect missing Ollama/model and offer explicit safe preparation. Failed download leaves a usable state and retry. Do not silently install system software or download a model.
2. On a clean account, install, open, complete the **new synthetic document** task from order and custom description, export a sample, quit, relaunch and recover drafts without a developer terminal. Test uninstall/reinstall, model update and user-data retention; check memory/disk based model selection.
3. Once required components/models are present, disconnect **all network interfaces** and repeat document creation and local chat. Confirm app/model endpoints remain loopback-only and capture outbound attempts. An HTTP loopback smoke or an old `/invoice-demo` run is not a disconnected new-product test.

Gate evidence: versioned artifact/checksum, reproducible build, fresh-install recording, new-workbench/relaunch result, supported-platform matrix, all-interface disconnected run and outbound capture. The existing macOS wrapper is reusable packaging evidence only until rebuilt with `/documents` and tested. No universal zero-setup or offline claim before the relevant tests pass.

## Phase 3 — controlled hosted document demo on the Mac mini

Owner: Worker A owns guarded service/model path; Worker B owns hosted journey; Auditor probes the full boundary.

1. Use an explicit HTTPS demo URL and bounded backend; Ollama stays on loopback and is never exposed directly. Reuse the proven session/queue/limit mechanisms only after document endpoints receive equivalent authorization, owner isolation, validation, request-size, rate, concurrency, queue, timeout, cancel and daily-cap checks. Old CSV API evidence does not certify the new routes.
2. Label all browser-submitted data as processed on the Mac mini, default to synthetic orders/descriptions and reject or clearly prohibit real customer documents until retention, deletion, logging, backup and incident handling are documented. The policy page must be reachable, accurate about persisted metadata and enforced fail-closed when unavailable.
3. Measure one, two and intended maximum simultaneous judges on the actual Mac mini: p50/p95 first response and end-to-end completion, failure rate, memory and recovery after Ollama stops/restarts. Set the public cap from results. Provide queue position/wait, useful busy/offline messages, health check and stop switch. Restart never marks incomplete jobs complete.
4. The authenticated ready→draft→review→sample export browser flow must be tested over the actual HTTPS/Secure-cookie boundary. Publishing an external service or changing firewall, certificates, accounts or permissions requires a separate concrete configuration/rollback review and the product owner's explicit approval. Keep access to an approved demo window; do not call the web edition offline.

Gate evidence: security/configuration review for **document** APIs, external HTTPS browser walkthrough, measured Mac mini load, data policy and fault/recovery recording. Existing CSV hosted API and local loopback tests remain reusable infrastructure evidence, not this gate's completion.

## Phase 4 — real issuance approval and SME pilot

Owner: Planner defines policy/pilot; Worker A implements trusted identity/persistence; Worker B connects approval UX; Auditor verifies.

1. Product owner selects a server-side identity provider, organization/issuer profile source, numbering scope, issue authority and whether manager approval is required. Distinct operator/manager accounts are authenticated; a demo role selector is not an authorization boundary. The default unavailable actor provider remains fail-closed until a real provider is connected.
2. The server enforces review/approval on exact order/source hash, document type, draft revision, terms, totals and export version. A material edit invalidates prior review/approval. Decisions record actor ID, organization, time, action, reason and immutable references; a creator/editor cannot self-approve where policy forbids it. Formal issue/number allocation and export follow the recorded policy. No automatic external send or payment is authorized by this phase.
3. A consented, de-identified or otherwise authorized SME pilot compares output with a human-reviewed answer set and records corrections, false approvals, missing fields/exceptions and recovery time. Define retention, deletion, backup and incident handling before any real data. Product owner approves broad release and any financial/external action separately.

Gate evidence: live identity, role/cross-organization/tamper tests, atomic issue-number and edit-invalidation tests, restart/persistence and immutable-log checks, exact export-byte comparison, pilot protocol/results and owner approval. Injection-based provider tests or demo reducer behavior are not live-auth evidence.
