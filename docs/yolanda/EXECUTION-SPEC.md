## 2. 目标、成果载体与不做的事

交付一页能实际操作的本地“Review & Approval”工作台。沿用当前 Next.js App Router、React、TypeScript、Tailwind；不是独立 HTML，也不是新建另一套应用。页面地址为 `/yolanda-review`，开发端口采用实际可用端口。

最终用户可以：确认 AI 的任务假设；核对原始证据；编辑识别字段、匹配关系和消息草稿；看见修改引起的结果失效与重新计算；审批某个明确版本；导出该批准版本的新文件。

实现顺序：先用合成数据完成真实交互和确定性规则，再通过小型 adapter 对接 JASON 的结果和 SAYA 的本地模型入口。模拟的是上游 AI 和身份，不是编辑、版本、阻塞、计算、审批和文件导出行为。所有模拟输入应明确标记。

本模块不负责 OCR、模型部署、多 Agent 编排、通用聊天、真实账号认证、消息渠道接入、真实邮件/WhatsApp 发送、付款、报税或回写账本。允许先做好草稿预览、批准、复制和下载；不把“先做出来”解释成授权真实外部发送。

不新增后端、数据库、消息队列、权限平台或通用工作流编辑器。普通浏览器下载足够；不为 CSV 导出增加 XLSX 依赖。

## 4. 角色与权限

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 操作员 reviewer | 修改业务参数、核对字段、选择匹配、编辑草稿、处理允许人工处理的异常、请求复核 | 自己取得 manager 权限、修改原始证据、发送消息、覆盖账本 |
| 经理 manager | 在拥有同等复核能力基础上审批当前结果、撤销当前批准、导出当前批准版本 | 批准已过期版本、跳过硬阻塞、授权本模块未实现的外部动作 |
| 模型/adapter | 返回建议值、候选匹配和草稿 | 授予权限、标记人工已复核、写入审批、改变固定政策 |

独立演示允许显式切换“演示操作员/演示经理”，始终显示“演示身份，非真实身份认证”。真实集成时隐藏演示入口，由宿主提供可信角色信息。前端按钮与 reducer 的检查只是原型行为约束，不构成安全边界；未来有服务器操作时，服务端必须重新核验身份、版本和操作权限。

固定政策：禁止外部发送、禁止覆盖原账本、禁止扩大文件访问、禁止云端回退。界面只读显示，不提供解除开关，聊天或提示词内容不影响政策。浏览器只能访问用户明确选择的文件或宿主明确提供的证据，不能读取任意路径。

## 5. 页面布局和操作步骤

页面使用英文主要标签，方便比赛演示；说明文档使用中文。继承项目现有视觉风格，优先复用只读引用的现有按钮和工具函数，不修改它们。

### 5.1 顶部

显示任务名、任务 ID、当前版本 `vN`、处理状态、阻塞数量、演示/真实数据标识、当前演示角色。显示“本模块不发送消息、不修改原账本”。不能固定显示系统离线或模型在线。

### 5.2 三个主要区域

1. `Task assumptions`：日期范围、日期解释、币种、字段映射、金额容差、候选日期窗口。每项区分“系统建议 / 用户已确认”，展示来源或假设理由。保存前校验，允许取消编辑。
2. `Review documents`：左侧单据列表及异常计数；中间只读原始证据与可编辑字段；右侧匹配候选、差异解释与人工处置。窄屏按顺序堆叠，不要求拖拽。
3. `Approve & export`：最终结果摘要、已排除记录、草稿、修改历史及当前版本。经理先读批准范围，再批准；批准后允许导出。

这三个区域可做简单 tabs 或页内区块，不增加路由系统或 UI 框架。计算中显示实际状态，按钮禁用须有文字原因；键盘可操作，有明确 label、焦点和错误提示，状态不能只靠颜色。

### 5.3 推荐操作链

载入合成批次 → 确认关键假设 → 查看来源与候选 → 更正字段或匹配 → 重新核对 → 处理阻塞 → 检查草稿及最终摘要 → 演示经理批准 `vN` → 导出 `vN`。

批准后再编辑任何影响结果的内容，界面立即撤销“当前有效批准”并禁用正式导出；旧批准只留在历史记录中。

## 6. 字段、编辑权限与重新计算矩阵

| 内容 | 可编辑项 | 保存后的处理 |
| --- | --- | --- |
| 业务日期 | 起止日期、歧义日期解释 | 增加版本，取消任务假设确认，重新确定纳入范围、匹配及草稿 |
| 币种 | 用户确认单一币种 | 增加版本，重新匹配和草稿；不自动换汇；异币记录转阻塞或有理由排除 |
| 字段映射 | 从已有列中映射日期、金额、币种、票据号等 | 增加版本，重新标准化、匹配、草稿；上游不支持时明确阻塞，不能假装重算 |
| 金额容差 | 非负、上限由固定政策限定的容差 | 增加版本，重新匹配、差异和草稿，不重新 OCR |
| 日期窗口 | 允许候选相差的天数 | 增加版本，重新匹配、差异和草稿，不重新 OCR |
| 单据识别值 | 商户、票据号、日期、金额、币种 | 增加版本，保存原建议与人工值，重算受影响结果和草稿 |
| 匹配关系 | 从合格候选中选择、撤销匹配、标记待核对 | 增加版本，检查台账记录占用，重算差异和草稿，不覆盖台账 |
| 异常处置 | 人工更正、确认警告、按规则排除 | 增加版本；要求理由；重算纳入范围和汇总 |
| 草稿文本 | 称呼、主题、正文、语气 | 增加版本，撤销批准；不重算金额或匹配；重新检查草稿 |
| 人工差异说明 | 原因、跟进备注 | 增加版本，撤销批准；不直接改变数值结论 |
| 原始证据 | 不允许覆盖文件、原文、来源位置或原始模型建议 | 只读；更换证据必须作为新输入事件，撤销批准并重新处理 |
| 固定政策 | 不可编辑 | 不接受来自表单、聊天、adapter 或导入文件的放宽 |

保存才提交有效更改；未保存表单也要阻止批准和导出，防止用户误以为正在批准屏幕中的新值。取消编辑恢复上次有效版本。无变化保存不增加版本。

任务参数、事实字段、匹配或纳入范围变化时，为简化首版实现，统一清除“批次人工复核完成”和“草稿已复核”标记；允许全批确定性重算，不为增量优化设计复杂依赖图。仅改草稿时保留数值计算，但清除草稿复核标记。

若修改了用户已手写的草稿所依赖的事实，不静默覆盖。保留旧文本，标记“来源已变化”，提供新建议与现有文本对照；用户选择采用或编辑后再确认。

## 7. 首版核对规则与异常政策

模块只处理单一指定币种的一对一“票据—台账行”核对。默认合成数据为 HKD；金额用整数分或精确十进制解析，不使用浮点近似相等，不换汇。

自动匹配的最小规则：币种一致、票据号规范化后精确一致、金额差不超过已确认容差、日期差不超过已确认窗口、只有一个候选且台账行未被其他有效匹配占用。示例默认金额容差为 0，日期窗口为 0 天，用户须确认。演示固定政策可限定金额容差最高 HKD 1.00、日期窗口最高 7 天；这是演示产品配置，不是会计标准，集成方必须确认后再用于真实业务。

缺票据号时可提出候选，但不直接自动匹配；用户有证据时可手动选择满足币种、金额和日期约束且未占用的候选，并填写理由。多个候选不能静默选择第一个。一个台账行不能被两张有效票据重复占用。

| 情况 | 处理 |
| --- | --- |
| 关键字段缺失、金额非法、日期歧义 | 硬阻塞；更正或有理由排除 |
| 多币种、负数/退款、拆分付款、一对多/多对一 | 首版不支持；标记并转人工，禁止强行归并 |
| 金额超容差、无合格匹配、多候选未决 | 阻塞该记录；核对更正或按规则排除，不以“经理批准”覆盖 |
| 疑似重复 | 不删除证据；阻塞到用户确认独立单据或排除其中一份并写理由 |
| 匹配冲突、旧计算结果、越权操作 | 不允许以“确认风险”绕过 |
| 非关键警告 | 有理由确认后可继续；保留警告及处置 |
| 原始证据不清楚/缺失 | 不能凭模型输出认定为真；补充新证据或有理由排除 |
| 空批次、所有记录均排除 | 不允许生成“处理成功”的批准结果；显示没有可批准记录 |
| 输入含 HTML、脚本或指令 | 按纯文本呈现；不得执行、不使用不可信 HTML、不接受文档内权限指令 |

排除并不等于成功处理：导出同时包含已纳入和已排除清单、数量、理由与未解决项。汇总明确仅针对已纳入记录；不得隐藏排除项以制造准确率。

## 8. 数据约定与上游交接

定义最小 TypeScript 类型到 `lib/yolanda-review/types.ts`，不要改组员的现有类型。单据使用稳定 ID，不能用数组序号代替业务标识。

| 对象 | 最少内容 |
| --- | --- |
| ReviewBatch | schemaVersion、batchId、revision、mode、来源版本、assumptions、documents、ledgerRows |
| Evidence | evidenceId、文件名、mimeType、原始文本/明确允许的本地来源、页码或原文片段；定位未知时明确为空，不能伪造 |
| ExtractedRecord | recordId、evidenceId、原始建议字段、人工覆盖字段、待核对原因 |
| LedgerRow | ledgerRowId、只读票据号/商户/日期/金额/币种 |
| MatchResult | recordId、候选 ledgerRowId、已选 ledgerRowId、匹配依据、差额、异常列表 |
| Draft | draftId、关联记录 ID、正文、依据版本、人工编辑状态、复核状态 |
| ChangeEvent | 事件 ID、时间、演示/真实操作者、操作、字段、修改前后值、理由、目标版本 |
| ApprovalSnapshot | approvalId、batchId、revision、批准时间、批准者标识及身份模式、冻结参数/结果/草稿/排除项、撤销记录 |

原始证据、模型建议、人工更正是三个不同层次。所谓“不可修改”是本模块不提供覆盖操作，并保留历史；本地前端记录不是不可篡改审计系统或法律签名。

adapter 使用普通函数或组件 props，最小约定：载入批次，以及按 `batchId + revision + requestId` 计算结果/更新草稿。不要擅自建立 HTTP API、假设 URL、添加认证接口或实现另一个模型客户端。

- JASON 提供单据、台账、候选与草稿的真实结果及错误；YOLANDA 提供数据约定和接收入口。
- SAYA 负责未来挂载入口、本地 API 连接和可信身份/策略注入；本次独立 route 不修改首页入口。
- demo adapter 必须显式使用合成输入；真实 adapter 不可用时显示未连接，不静默退回假结果。
- 外部数据在入口校验：schemaVersion、唯一 ID、引用存在、金额格式、日期、字段长度和批次数量。演示建议上限为 100 条、JSON 文件 2 MB、单段草稿 10,000 字符；超限给明确错误，不截断成看似成功。
- adapter 不得带入已批准、已人工确认或扩权标记；这些状态只能由本模块允许的用户动作产生。模型自报置信度可作提示，不能当作已校准概率或批准条件的唯一依据。

## 9. 状态、版本和批准语义

保持一个明确状态模型，可使用 `useReducer` 和少量纯函数，不引入状态库。

主状态：`draft`、`calculating`、`review`、`approved`、`error`。阻塞、脏表单、复核标记、当前计算版本是明确数据；`canApprove` 和 `canExport` 用同一组纯函数推导，不到处复制条件。

1. 载入新批次进入 draft，revision 从正整数起。关键假设未确认时不能批准。
2. 任何有效内容变更使 revision 单调增加，旧批准立即失效并留在历史。
3. 需要重算时清除旧结果的“当前有效”资格，进入 calculating；旧结果可只读查看，但标明过期。
4. 每次计算捕获 batchId、revision、requestId。只有三项都等于当前请求的响应才能应用；切换批次、第二次计算、修改或取消后返回的旧响应必须忽略。
5. 最新计算成功进入 review。失败进入 error；重试不得伪装为批准完成，也不得使用旧成功结果通过检查。
6. 可批准条件：演示/可信 manager、无未保存编辑、关键假设已确认、非计算中、计算版本有效、至少一条纳入记录、无硬阻塞、数值结果及需导出的草稿已人工复核。
7. 批准动作先再次检查条件，冻结整个批次的结果快照，显示“批准 vN：仅供导出和人工后续使用，不授权发送或付款”。
8. 导出动作再次检查当前有效批准，读取冻结快照，不读取正在变化的界面状态。构建文件期间禁止结果编辑，或先同步取得完整不可变快照再构建文件；不能混合 vN 与 vN+1。
9. 修改、撤销批准后，当前页面不允许再以有效批准名义导出旧版本。历史可查看，但不得让历史记录看起来仍然有效。
10. 已下载的文件无法被程序召回。文件必须包含 batchId、revision、approvalId 和时间，界面说明修改后应重新导出。

首版选择“整批批准”，不做逐条签批、多级审批、代理审批。审批留痕与真实身份验证分开表述。

## 10. 导出、暂存和数据保留

批准后提供三个新文件下载：

- `ezagent-<batchId>-v<revision>-review.json`：结构化结果、参数、来源引用、修改记录、批准标识、排除项和模拟标记。
- `ezagent-<batchId>-v<revision>-results.csv`：结果表，含状态、原值/更正值、匹配对象、差异、排除理由与批准版本。
- `ezagent-<batchId>-v<revision>-drafts.txt`：可读消息草稿及关联版本，不含已发送状态。

CSV 正确处理引号、逗号、换行和 UTF-8；不可信文本列防止电子表格公式注入，覆盖 `= + - @` 及前导空白/控制字符变体。数值列先严格解析为数值再输出，不将任意输入伪装为数值。JSON 保留原始数据供追溯，不因 CSV 显示防护丢失原值。

使用浏览器 Blob 下载并清理 object URL。不提供任意系统输出路径，不覆盖原文件。浏览器无法可靠证明用户已保存文件，状态写“已生成下载”，不写“已成功保存到硬盘”。

首版会话数据默认仅存在内存；刷新会丢失未导出进度，应明确提示。提供“保存工作副本 JSON”，允许批准前下载，并显著标记 UNAPPROVED，不得与正式批准导出混淆。支持从本模块工作副本恢复；导入必须经过校验，带入的审批/身份不被信任，按待复核状态恢复，原批准只作来源历史。不要把敏感数据自动存入 localStorage、云端或远程日志。

清空任务前提示未保存内容；清空仅清本模块会话，不删除原始文件或已下载文件。不记录完整敏感内容到 console。

## 11. 合成演示批次和验收用例

准备至少 8 个有明确预期的案例：唯一匹配、金额识别错误、日期歧义、重复票据、多候选、无匹配、币种不支持、恶意文档文字。数据不得含真实客户或未经授权的票据。

## 12. 执行步骤与每次本地 Git 存档

先阅读本地 AGENTS.md（如有）、本规格、同目录 CONTEXT.md、现有代码和 Git 历史。不要把当前网页说明当成真实实现。

每次执行开始：

1. 验证当前路径、仓库根、分支和 HEAD；记录 `git status --short`，确认工作区归属。
2. 有组员或未知修改时不暂存、不 stash、不 reset、不清理；用当前已提交基线建立独立 worktree/副本，保留原状。
3. 只续做已有 YOLANDA 任务目录的已知修改；先确认已有阶段成果，避免重做。
4. 记录本次可观察目标和允许修改的文件。

实施阶段：

- P1：最小类型、合成案例、匹配与验证纯函数、版本状态及关键测试。
- P2：独立 route、任务假设、来源核对、字段编辑和匹配操作。
- P3：草稿、批准快照、失效规则、工作副本和正式导出。
- P4：错误/竞态/a11y 验证、实际演示、集成说明和最终交接。

每阶段完成且本次执行结束前：

1. `git diff --name-status` 与 `git status --short` 检查范围；运行必要检查。
2. 用明确文件名或确认归属的白名单目录执行 `git add -- <paths>`，禁止 `git add .` / `git add -A`。
3. 检查 `git diff --cached --name-status` 和 `git diff --cached --check`；暂存区不得出现白名单外文件、依赖、真实业务数据或凭证。
4. 本地 commit，消息表明范围与状态。未完成但可保存的独立阶段用 `wip(yolanda): ...`，并在交接中说明未通过项，不能伪称完成。
5. 输出 commit hash、分支、改动范围、检查结果、未解决问题和下一步。确认工作区状态；不推送。

已授权本地提交，无需每一步再次要求用户确认。若 Git 身份未配置，使用已有有效身份；不得借用组员身份。可用本次命令范围的自动化身份 `git -c user.name=Codex -c user.email=codex@localhost commit ...`，注明自动化代提交，不改全局设置。

禁止 force、reset --hard、clean、自动合并/重写历史、未经授权删除文件或更改 .gitignore。若需要扩大白名单，先交付可独立运行的部分，列出具体集成补丁需求，让用户或对应负责人决定。
