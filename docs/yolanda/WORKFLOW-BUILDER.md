# YOLANDA 工作流配置器

日期：2026-10-07

## 产品边界

`/yolanda-builder` 用于创建、确认和保存可复用的工作流配置。它本身不处理真实票据、不批准业务结果，也不发送消息或覆写文件。受支持的发票配置可在保存后交给既有 `/invoice-demo` Agent；交接只导航和载入配置，不直接执行。原 `/yolanda-review` 财务复核与审批示例继续独立存在。

配置流程只有三个步骤：

1. 从发票输出示例开始，或描述其他重复工作；其他场景会在首步说明执行能力尚未接入。
2. 只确认严格金额门槛、接受币种、缺失字段处理等关键决定，并在规则旁查看内置小例子的即时变化。
3. 阅读由同一份配置生成的说明卡，命名并保存到浏览器 IndexedDB；可从“本机工作流库”重新打开。

普通用户通过“规则预演”观察当前模板支持的结构化参数。发票门槛例子使用与执行器相同的严格大于比较；USD 例子按接受币种纳入或转人工；缺失字段例子按配置转人工或保留空值并标记。收据模板仍可预演日期解释。结果绑定 `workflowId + revision + requestId + caseVersion`，配置变化后旧结果不得覆盖新版本。自由文本规则会明确标记为“仅记录，尚未映射”；内置例子通过不代表整个工作流已验证。

原结构化 JSON 工具改称“开发验证：结构化 JSON 校验”并默认折叠。它只校验最多 100 笔、256 KB 的固定票据资料结构，可下载防公式注入 CSV；不是规则预演、PDF／图片 OCR 或实际工作流运行。缺少币种会转人工，不会静默补成 HKD。

## 本机工作流资产管理

页面顶部“本机工作流库”默认只突出名称、用途、最近修改时间、配置状态、预演状态、执行能力和“打开”。公司、部门、创建者、revision 与角色权限收进“管理详情”；永久删除收进详情中的折叠菜单，并保留确认与权限检查。

演示组织角色分为员工、组长、部门经理和组织管理员。员工可查看与按策略试跑；组长可创建和编辑本部门工作流；部门经理可删除本部门工作流；组织管理员可跨部门管理，并设置最低试跑与编辑角色。职位名称不直接授予权限。

上述角色切换和权限判断都只发生在浏览器前端，用于验证产品交互，不是真实身份认证或生产授权。旧版本机工作流缺少治理资料时显示“未知”，不会编造创建者或历史时间；首次重新保存后由当前演示身份建立本机归属记录。

当前“整理成步骤”使用公开、确定性的本地规则。页面明确说明它不是模型理解。SAYA 接入真实本地模型前，不得把候选配置描述成 AI 已经理解或可以执行。

第一步提供简短本机 AI 状态和默认折叠的准备入口。自动检查是只读操作；安装、下载或启动必须由用户明确触发。模型就绪与当前工作流是否受 Agent 支持是两项独立状态。

## 单一配置源

`lib/yolanda-review/workflow-config.ts` 定义 schema `1.2` 的 `WorkflowConfig`。结构化参数可包含日期解释、接受币种、缺失字段处理和发票金额门槛；规则使用 `mapped`／`recorded-only` 标明是否已映射。模板预设标记为 `template-default`，不会冒充 `user-request`。

页面说明卡、完整提示词、规则预演、高级配置 JSON、备份文件、IndexedDB 记录和交接数据都只从该配置派生。提示词不是第二份配置，也不授予工具权限。

规则变化推进 revision 并清除确认；无变化保存不推进 revision。名称变化推进 revision，但可继承同一组已确认行为规则的确认状态。重新整理需求时，`user-edit` 条目与已回答问题按稳定 ID 保留。候选结果只有在 requestId 与来源 revision 仍匹配时才能应用。

## 本机保存接口

`lib/yolanda-review/workflow-storage.ts` 暴露：

- `saveWorkflow(config)`；
- `listSavedWorkflows()`；
- `getSavedWorkflow(workflowId)`；
- `saveWorkflowVersion(config)`。

当前 adapter 使用 IndexedDB 的 `workflows` 与 `workflowVersions` 两个 object stores，分别保存最新版本和版本记录。只保存配置和必要元数据，不保存票据正文、密钥或可信身份。

读取旧浏览器记录时会在存储边界迁移缺少的 `mapping` 与 `previewParameters`，保留原规则和治理资料，同时增加 revision、清除旧确认并将执行能力重置为未接入。用户不需要清除浏览器资料。

配置导入限制为 256 KB、50 条规则和 20 个待确认问题。导入时校验 schema、稳定 ID、集合归属和字段长度，并清除配置确认和执行能力信任。旧 `1.0`／`1.1` 配置会保留原规则、升级为 `1.2`，新增预演参数保持待确认；原始文件不被覆写。导入不会执行工作。

## 交接责任

- 发票 Agent：通过 `workflow-agent-handoff.ts` 接收单一币种、严格金额门槛和缺失字段策略；从保存接口读取精确工作流版本，再由既有 Planner、Run validator 与执行器处理。
- SAYA：把需求文本送入本地模型，返回候选 `WorkflowConfig` 与待确认问题；宿主仍需执行版本和策略检查。
- 工具库负责人：通过保存接口列出和打开配置；不要复制页面内部 state 或解析提示词反推配置。

发票模板只有在工作流已确认、币种唯一、缺失字段使用 Agent 固定人工检查政策，且不存在影响结果的未映射规则时，才可交给 Agent。日期解释、发送／分派等额外动作与任意未映射自由文本不会被静默忽略；它们会列入未支持要求并阻止以“完整工作流”名义运行。`receipt-json-preview-v1` 仅保留为开发资料校验。其他场景仍可保存配置，但不显示可以运行。
